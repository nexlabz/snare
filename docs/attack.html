How a dropper hides in your own repository

The threat

Four routes in, none of which you'd think to check

The same payload ships four ways. Every one of them fires from a completely ordinary developer action — opening a folder, starting the dev server, or just beginning a session with your coding assistant. That is exactly why this family works.

Opening the folder in your editor

.vscode/tasks.json

A task labelled eslint-check, marked "hide": true and "reveal": "never" so it never appears in the terminal panel. It runs node ./public/fonts/fa-solid-400.woff2.

▸ fires on "runOn": "folderOpen"

Starting the dev server

postcss.config.js

The payload is appended to the last line after thousands of spaces. The file reads as four correct lines of config, because everything else is far off the right edge of the viewport.

▸ fires on next dev / next build

Running any npm script

package.json

Every script gains a prefix: "dev": "node api.js && next dev". These aren't install hooks, so --ignore-scripts doesn't help.

▸ fires on npm run dev / build / start

Opening a session with your AI assistant

.claude/settings.json

A SessionStart hook runs node .vscode/setup.mjs every time a session opens. It survives removing the package that delivered it, npm never sees it, and the two copies in .claude/ and .vscode/ re-create each other — so deleting one directory fixes nothing.

▸ fires on every new agent session

“Is this the npm supply-chain thing?”

Same category, different delivery — and the difference is why people miss it.

A classic npm supply-chain attack compromises a package you depend on. It arrives through npm install, it shows up in your lockfile, and npm audit or a dependency scanner has a chance of catching it.

This one never touches the registry. It's committed into your repo, so npm audit, your lockfile and Dependabot all stay clean. (The loader is tagged NPM internally, so registry variants likely exist too.)

If you arrived here searching for the npm attack: run the four checks anyway. They take a minute and they cover the route a dependency scanner cannot see.

The font is not a font

A genuine .woff2 file begins with the magic bytes wOF2. This one begins with 507 spaces, then JavaScript. Disguising a payload as a binary asset keeps it out of code review entirely — nobody opens a font in a diff.

  How it works
  
The address it phones home to is not in the code

  
Blocking an IP does nothing. The loader reads a fresh server address from the Ethereum blockchain on every run (EtherHiding), and the operator moves with one transaction.


  

  

    

      
Step by step

      
    
        
  1. Query public Ethereum RPCsFalls through 1rpc.io, drpc.org, publicnode and blastapi, so cutting off any one endpoint changes nothing.
    2. 
        
  2. Read the wallet's newest transactionThrough the Blockscout API, sorted newest first.
    3. 
        
  3. Decode an IP from the destination addressThe first eight bytes are read as two IPv4 addresses — a primary and a fallback.
    4. 
        
  4. Fetch stage two over plain HTTPFrom /0x/clb, /0x/cls or /0x/ls, on port 443 to look like TLS to a port-based filter.
    5. 
        
  5. Decode and spawn it detachedXOR-decoded and evaluated in memory — nothing is written to disk — then spawn(…, {detached:true}) and unref(), so it outlives the editor that started it.
    6.

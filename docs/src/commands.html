Reference

Every command, and what it will not do

snare is about 2,200 lines of bash. No framework, no npm install — deliberately, because npm is the attack surface. The core heuristic is language-agnostic; the config list is tuned for the JavaScript ecosystem, because that is where this family lives.

Guided clean-up

The guided one

If you do not want to choose between the commands below, this runs the whole sequence and asks you at each step. It is the same work, in the order that actually helps.

Guided clean-up
snare respond                   walk through everything, one question at a time
snare respond --status          where you got to
snare respond --reset           start the walkthrough again

Six steps, then a verification pass that re-reads rather than trusts. Writes default to no, purging history is asked once, and progress is saved.

It refuses to run unattended. With no terminal, or CI set, it exits rather than prompting where nobody can answer — use the individual commands there.

Find it

Scanning

Scanning
snare scan                      scan the current directory
snare scan repo [path]          one clone: working tree, all branches, full history
snare scan repo [path] --new    only findings that are not in the baseline
snare scan orgs                 list every org/account you can reach, with repo counts
snare scan orgs --all           include individual accounts, not just organisations
snare scan github               every repo you can reach, via the API (no cloning)
snare scan github --pick        choose which orgs to scan, from a list
snare scan github --owner a,b   only these orgs/accounts (comma-separated)
snare scan github --mine        only repos you own
snare scan github --all-branches
snare doctor                    this machine, persistence spots, and your GitHub account
snare selftest                  prove detection still works against known samples

Don't scan everything first. One real account reached 22 organisations and ~950 repositories. scan orgs lists what's reachable and how big each owner is; scan github --pick lets you choose.

Read before trusting a clean result. scan github reads branch tips through the API: no history, a bounded set of files. scan repo on a real clone walks every branch and commit. The original infection survived a clean 127-repo API sweep and was caught only by scan repo.

selftest runs the real scanner on known-bad and known-good samples and fails on any mismatch. If it fails, trust no clean result.

Stop it coming in

The gate, for you and for coding agents

Gate · agents
snare agents install            gate every clone, pull, install and run an agent does
snare agents status | uninstall
snare agents install --project  also this repo's CLAUDE.md / AGENTS.md and a project hook
snare gate -- <command>         scan first; exit 0 means safe to run it
snare gate allow [dir [branch]|url]  you looked and it is yours: allow what was flagged,
                                on disk or still incoming (a branch, a pull, a clone)
snare gate allowed | forget     review or withdraw what you allowed
snare gate report               the last block, word for word, to paste into an agent

A block is a suspicion, not a verdict. It lists file, line and why. Look, then decide: snare gate allow if it's yours, snare respond if not. Approvals live in ~/.snare and lapse if the file changes. A coding agent can't approve its own block.

The gate scans code before a command brings it in or runs it. git clone goes to quarantine first; pull, merge, rebase and checkout are scanned in a throwaway worktree before a file lands; installs and npm run scan their directory. If the scan can't finish, the command doesn't run.

For coding agents, snare agents install adds an enforced Claude Code PreToolUse hook, plus instructions in CLAUDE.md, AGENTS.md and GEMINI.md. A block says "FIRE ON THE MOUNTAIN" and raises a notification. Ordinary commands cost ~30ms. It asks before installing; snare agents uninstall removes it for good.

Every ecosystem

Known-malicious packages: npm, Python, Rust, Go and more

Deps
snare deps [dir]                 lockfiles, node_modules and virtualenvs against the list
snare deps --system              also your global Python, pipx, npm and cargo installs
snare deps fix [dir]             remove each one, or replace it with a version not listed
snare deps update | status       refresh / show the known-malware list

The list is OpenSSF's malicious-packages (~117,000 packages across npm, PyPI, crates.io, Go, RubyGems, Packagist, NuGet, Maven), refreshed every six hours. Matching happens on your machine; nothing about your packages is sent. It reads the lockfiles of all of those ecosystems.

The gate uses the same list to stop npm i, npx, pip install, uv add, cargo add, go get, gem install and composer require on a listed version, and checks lockfiles before an install. It also watches files other languages run on their own: setup.py, conftest.py, build.rs, sitecustomize.py, .pth and //go:generate.

Stop it running

Guard and shield

Guard · shield
snare guard install             kill the loader on sight, from login onwards
snare guard scan                one-shot check of this machine
snare guard status | log | stop | start | restart | uninstall

snare shield install            scan before npm/pnpm/yarn/bun/npx and git clone run
snare shield status | uninstall
snare shield check [path]       the fast check on its own (~22ms)

The guard runs in the background (launchd, systemd user unit, or a logon task on Windows). It polls every second, so a payload can act first, and it can't see code inside another process.

The shield wraps package managers in your shell so they're scanned before running. Shell only: it can't see VS Code's folderOpen task, and command npm bypasses it. A seatbelt, not a sandbox.

Stop it spreading

Hook and CI

Hook · CI
snare hook install              block a push that carries a payload
snare hook install --with-pre-commit
snare hook status | uninstall

snare ci install                write a GitHub Actions workflow into this repo
snare ci status                 is the workflow installed, and is the check required?
snare ci print                  print the workflow without writing it

This family injects into commits as they leave an infected machine. The hook is the only feature that prevents that rather than detecting it later, and it refuses a push while the machine has a live detection.

GitHub.com can't reject a push outright, so a required status check does the job: the merge button stays disabled until the scan passes. ci install writes the workflow; you must mark it required under Settings → Branches. snare ci status tells you if you haven't.

Clean up

Fix, rotate and notify

Fix · rotate · notify
snare fix <owner/repo>                        dry run (always backs up first)
snare fix <owner/repo> --push                 clean branch tips and push
snare fix <owner/repo> --purge-history --push erase it from all history
snare fix --all                               every repo the last scan flagged
snare fix --pick                              choose orgs, scan them, then fix
snare fix --pick --purge-history --push       ... and erase it from all history
snare fix --owner a,b --push                  the same, without the prompt

snare rotate                    what to revoke, in order, plus a GitHub audit
snare notify <owner/repo>       list collaborators and preview the notice
snare notify <owner/repo> --issue | --mail

Rotate before you clean. Credentials are the target; the file is only delivery. snare rotate lists what to revoke, npm write tokens first, and audits your GitHub account for what this family leaves behind. Full order on the response page.

fix --pick is the whole clean-up in one pass: choose organisations, scan, remediate. It's a dry run unless you add --push, and destructive flags stay visible on the command line. --owner a,b does the same without the prompt. --purge-history checks for git-filter-repo before scanning.

--purge-history changes every SHA: collaborators re-clone, and forks and PR refs keep old objects. fix --all is a dry run and makes you type the repository count.

Keep watch

Reports, baseline and update

Reports · baseline · update
snare report                    scan, save a timestamped report
snare report --json             machine-readable; exits non-zero on findings
snare schedule install --daily  run it on a timer and notify on findings
snare schedule status | uninstall

snare baseline set              accept the current findings as known
snare baseline status | clear

snare update                    pull the latest version
snare update --check            is a newer version available?
snare update --mode auto        install new versions itself (default: notify, or off)
snare update --relink           point ~/.local/bin/snare at this checkout
snare version                   version and commit

Reports go to $SNARE_HOME/reports and exit non-zero on a finding, so timers and CI can act. No email, on purpose: SMTP credentials are a liability.

Accepting a finding into a baseline silences it — it does not make it safe. Only baseline what you have actually read.

Installed before 27 August 2026? Those versions could report clean on infected repos. Run snare update, then snare selftest. The changelog lists each defect.

Limits

What snare does not do

A security tool that oversells itself is worse than no tool at all.

The guard polls every second, so a payload can act first; it can't see inside other processes and will miss variants on new infrastructure. Removing the malware is the fix; a running guard is never permission to open a repo you don't trust.

Scanning through the GitHub API sees branch tips only. A payload that was committed and later deleted survives in history; use snare scan repo on a clone to catch that.

Rewriting history does not touch forks, pull-request refs, or objects still reachable by SHA. Ask GitHub Support to garbage-collect after a purge.

Found a hole? Report it — that is the whole ask

A false clean is the worst failure a scanner can have, and the one we most want to hear about.

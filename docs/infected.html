What to do, in the order that matters

The instinct is to clean the repositories first. That is the wrong order, and on an infected machine it is wasted work — this family injects into commits on their way out, so it re-infects whatever you just cleaned.

The short way

One command walks you through all of it

Everything on this page, asked one question at a time, in the right order. Nothing is changed or pushed without you saying so, and it saves your place if you stop.

Start here
snare respond

What it will and will not do

It revokes npm tokens in one keypress, opens the pages it can't act on, and asks before every push. Writes default to no. Purging history is asked once, not per repository.

If you skip rotating credentials it carries on, but reminds you before anything is pushed and again at the end.

snare respond --status shows where you got to. snare respond --reset starts again.

The rest of this page is the same sequence done by hand. Read it if you would rather drive, or if you want to know why the order is what it is.

The order

Four steps, and the sequence is the point

  1. Rotate your credentialsThe file in your repo is only delivery; removing it doesn't un-steal a token. npm write tokens first: a stolen one publishes trojaned versions of your packages under your name.
  2. Clean the machine you push fromBefore touching any repository. If several repositories are flagged, the common factor is almost always the machine that pushed to them, not several separate accidents.
  3. Then clean the repositoriessnare fix is a dry run by default and always backs up first. Only add --push once you have read what it would change.
  4. Then tell your collaboratorsThey may be infected from the same source, and if you rewrote history their clones will break with no explanation.
Step 1

Rotate

Do this first
snare rotate        # the ordered checklist, plus a GitHub audit

npm tokens first (npmjs.com/settings/~/tokens, write and "bypass 2FA"), then GitHub PATs, OAuth apps and SSH keys, then cloud keys (AWS incl. Secrets Manager in every region, GCP, Azure), then anything the process could read: .env files, kubeconfig, Vault, database URLs, AI keys, wallets. Treat anything you copied to the clipboard while infected as seen.

Step 2

Clean the machine

Before touching any repo
snare doctor          # machine, persistence spots, your GitHub account
snare guard scan      # one-shot process check
snare guard install   # kill the loader on sight, from login onwards

A clean guard scan doesn't mean you were never infected. The loader runs during a build or folder open, then exits. Clean process, infected repos: that's expected.

Step 3

Clean the repositories

Dry run first — always
snare fix owner/repo                        # dry run, changes nothing
snare fix --all                             # dry run over everything flagged

snare fix owner/repo --push                 # clean the branch tips
snare fix owner/repo --purge-history --push # erase it from all history

--purge-history changes every SHA. Collaborators must re-clone; a pull will conflict or bring old objects back. Forks and PR refs keep the old objects unless GitHub Support garbage-collects them.

Afterwards, verify rather than assume. snare scan github only reads branch tips; run snare scan repo against a fresh clone to walk full history.

Step 4

Tell the others

Contacts and templates
snare notify owner/repo             # list collaborators, preview the notice
snare notify owner/repo --issue     # file a GitHub issue @-mentioning them
snare notify owner/repo --mail      # open a pre-filled mail draft per person

Both templates lead with rotation and say it isn't an accusation: whoever's commit carried it was almost certainly a victim. Say that early.

If the count is high

If a lot of repositories are flagged

Fifteen infected repositories is not fifteen accidents. It points at one machine that pushed to all of them. Work out which machine that is before cleaning anything, or you will clean the same repositories twice.

How this family first reaches a machine is still unknown. If you can name what you scaffolded an infected project with (a template, create-*, theme or extension), say so in the discussion.

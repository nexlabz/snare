Chapter 01The attack6 min read

How the attack works

The threat

Four routes in, none of which you'd think to check

The same payload ships four ways. Every one of them fires from a completely ordinary developer action — opening a folder, starting the dev server, or just beginning a session with your coding assistant. That is exactly why this family works.

Opening the folder in your editor

.vscode/tasks.json

A task labelled eslint-check, marked "hide": true and "reveal": "never" so it never appears in the terminal panel. It runs node ./public/fonts/fa-solid-400.woff2.

▸ fires on "runOn": "folderOpen"

Starting the dev server

postcss.config.js

The payload is appended to the last line after thousands of spaces. The file reads as four correct lines of config, because everything else is far off the right edge of the viewport.

▸ fires on next dev / next build

Running any npm script

package.json

Every script you had is still there, each one now prefixed: "dev": "node api.js && next dev". The obfuscated api.js sits at the repository root. Nothing has to be installed for this to run, so --ignore-scripts makes no difference — these are not install hooks.

▸ fires on npm run dev / build / start

Opening a session with your AI assistant

.claude/settings.json

A SessionStart hook runs node .vscode/setup.mjs every time a session opens. It survives removing the package that delivered it, npm never sees it, and the two copies in .claude/ and .vscode/ re-create each other — so deleting one directory fixes nothing.

▸ fires on every new agent session

“Is this the npm supply-chain thing?”

Same category, different delivery — and the difference is why people miss it.

A classic npm supply-chain attack compromises a package you depend on. It arrives through npm install, it shows up in your lockfile, and npm audit or a dependency scanner has a chance of catching it.

This one never touches the registry. The payload is committed into your own repository, so there is no malicious dependency to find — npm audit is clean, your lockfile is clean, and Dependabot has nothing to report. The malicious code is sitting in a file your build already loads. Interestingly, the loader carries an internal vector tag reading NPM, so the same operator appears to run registry-delivered variants as well.

If you arrived here searching for the npm attack: run the four checks anyway. They take a minute and they cover the route a dependency scanner cannot see.

The font is not a font

A genuine .woff2 file begins with the magic bytes wOF2. This one begins with 507 spaces, then JavaScript. Disguising a payload as a binary asset keeps it out of code review entirely — nobody opens a font in a diff.

Why nobody spotted it

Here is the actual shape of an infected postcss.config.js. Four ordinary lines, then a gap wide enough to push the payload past any screen. Reveal the whitespace to see what your editor was not showing you.

  How it works
  
The address it phones home to is not in the code

  
This is why blocking an IP achieves nothing. The loader ships with no server
  address at all — it derives a fresh one every run by reading the public Ethereum blockchain, a
  documented technique known as EtherHiding. The operator moves their infrastructure by
  sending a single transaction.


  

  

    

      
Step by step

      
    
        
  1. Query public Ethereum RPCsFalls through 1rpc.io, drpc.org, publicnode and blastapi, so cutting off any one endpoint changes nothing.
    2. 
        
  2. Read the wallet's newest transactionThrough the Blockscout API, sorted newest first.
    3. 
        
  3. Decode an IP from the destination addressThe first eight bytes are read as two IPv4 addresses — a primary and a fallback.
    4. 
        
  4. Fetch stage two over plain HTTPFrom /0x/clb, /0x/cls or /0x/ls, on port 443 to look like TLS to a port-based filter.
    5. 
        
  5. Decode and spawn it detachedXOR-decoded and evaluated in memory — nothing is written to disk — then spawn(…, {detached:true}) and unref(), so it outlives the editor that started it.
    6. 
      

    

    

      
Address → endpoints

      

        
20-byte destination address

        

          

            a322e5f3
            d311d308
            e6f01210
            63e9aDC2
            490Ef1a…
          

          

            bytes 0–3 → primary C2
            bytes 4–7 → fallback
            remainder unused
          

        

      

      
The payload observed in the wild stole clipboard contents — passwords, access
      tokens and wallet seed phrases — from the moment the editor opened.

Chapter 02Check your machine3 min read

  
Seven checks you can run right now

  
No tools required, nothing to install. Run these against any clone on your
  machine — the whole thing takes a couple of minutes. Every command is read-only; none of them change
  anything.










  

    
1 · Is a loader running right now?

    
macOS · Linux

      
ps -eo pid,args | grep -E "node .*-e .*global\[" | grep -v grep

    
No output means nothing is running. Any output is a live process — kill it.

  


  

    
2 · Does any file carry the operator's wallet?

    
working tree

      
grep -rn "0xa322E5f3D311D3080e6f0121063e9aDC2490Ef1a" .

    
and the full history — a deleted file still lives in Git

      
git log --all -S "0xa322E5f3" --pickaxe-regex --oneline

  


  

    
3 · Is a task set to run when you open the folder?

    
editor auto-run

      
grep -rn "folderOpen" .vscode/tasks.json

    
Any hit executes the moment the folder opens. Treat it as hostile until proven otherwise.

  


  

    
4 · Are your font files actually fonts?

    
magic bytes

      
head -c 4 public/fonts/*.woff2

    
Every real font prints wOF2. Spaces mean you are looking at a script.

  


  

    
5 · Do your npm scripts run something extra?

    
This family leaves every script you had and prefixes each one, so the file still looks
    like yours. The payload runs on npm run dev — no install needed, which is why
    --ignore-scripts does not help.

    
run scripts

      
node -e 'const s=require("./package.json").scripts||{};
for (const [k,v] of Object.entries(s)) if (/\bnode\s+\S+\.[cm]?js/.test(v)) console.log(k, "->", v)'

    
A build step calling your own scripts/build.js is normal. A root
    api.js or app.js you did not write is not — open it and look at the
    first line.

  


  

    
6 · Does your AI assistant run something at every session?

    
An agent's own config is an execution vector, and removing the package that delivered the
    hook does not remove the hook.

    
agent hooks

      
cat .claude/settings.json .claude/settings.local.json 2>/dev/null
ls -la .claude/setup.mjs .vscode/setup.mjs 2>/dev/null

    
A hook you wrote — a formatter, a linter — is fine. node
    .vscode/setup.mjs is a dropper, and the copies in .claude/ and
    .vscode/ re-create each other, so remove both.

  


  

    
7 · Has someone rewritten your remote?

    
The remote tip comes back with your commit's subject, author and date under a different
    hash. Git reports 1 ahead, 1 behind with identical messages, which reads as
    harmless — and then a pull merges it.

    
forged force-push

      
git fetch && git log --format='%H %cI %s' HEAD..@{u}
git log --format='%H %cI %s' @{u}..HEAD

    
Same message and author date on both sides, but a different hash and a
    committer timezone that is not yours? Do not pull.

  


  

    
Look for the long line

    
The most reliable giveaway is geometry, not content. This finds any file padded out to hide
    something past the edge of the screen — a hand-written config has no business being 9,000
    characters wide.

    
hidden-payload heuristic

      
awk 'length > 1500 {print FILENAME": line "FNR" ("length" chars)"}' \
  $(find . \( -name "*.js" -o -name "*.mjs" -o -name "*.cjs" \) -not -path "*/node_modules/*")

  






  What the result means
  
Read the outcome carefully

  

    
      Something matched
      Go to the response plan
      
Do not clean the repository first. Rotate your credentials before anything else — the
      order genuinely matters, and getting it wrong means doing the work twice.

    
    
      Nothing matched
      Install snare to keep it that way
      
These seven checks cover one clone at one moment. snare runs them continuously, across
      every repository you can reach, and blocks a push that would carry a payload out.

    
  

  

    
A clean result is narrower than it looks

    
Checks 2, 3 and 4 test one clone — not your other repositories, and not the
    branches you do not have checked out. Check 1 reports what is running right now; the
    loader fires when a build runs or an editor opens the folder, does its work, and exits, so a
    quiet process list alongside an infected repository is the expected result, not a
    contradiction.

    
These checks also key on this operator's wallet. A variant using a different address
    passes check 2 and is still caught by the long-line heuristic above — which is why that one
    matters most.

Chapter 03If you're infected4 min read

  
What to do, in the order that matters

  
The instinct is to clean the repositories first. That is the wrong order, and on
  an infected machine it is wasted work — this family injects into commits on their way out, so it
  re-infects whatever you just cleaned.










  The short way
  
One command walks you through all of it

  
Everything on this page, asked one question at a time, in the right order.
  Nothing is changed or pushed without you saying so, and it saves your place if you stop.

  
Start here

    
snare respond

  

    
What it will and will not do

    
It revokes what it safely can — npm tokens are one keypress, and they are the ones that
    matter most — opens your browser at the pages it cannot act on, and asks before every push.
    Anything that writes to a repository defaults to no. The destructive choice,
    whether to purge history, is asked once rather than per repository, so a
    rhythm of "yes" cannot carry you through it by accident.

    
It will not pretend to have rotated your credentials for you. It asks, and if you say no it
    carries on — but it tells you again before anything is pushed, and again at the end. A step
    that blocks you is a step you abandon.

    
snare respond --status shows where you got to.
    snare respond --reset starts again.

  

  
The rest of this page is the same sequence done by hand. Read it if you would
  rather drive, or if you want to know why the order is what it is.






  The order
  
Four steps, and the sequence is the point

  
    
    
  1. Rotate your credentialsStealing them is the objective; the
    file in your repository is delivery, not payload. Removing it does not un-steal
    a token. npm write tokens first — a stolen one lets the worm publish
    trojanised versions of your other packages under your name, which is how one
    laptop becomes a supply-chain incident.
    2. 
    
  2. Clean the machine you push fromBefore touching any
    repository. If several repositories are flagged, the common factor is almost
    always the machine that pushed to them, not several separate accidents.
    3. 
    
  3. Then clean the repositoriessnare fix is a dry
    run by default and always backs up first. Only add --push once you
    have read what it would change.
    4. 
    
  4. Then tell your collaboratorsThey may be infected from the
    same source, and if you rewrote history their clones will break with no
    explanation.
    5. 
  






  Step 1
  
Rotate

  
Do this first

    
snare rotate        # the ordered checklist, plus a GitHub audit

  
In order: npm tokens
  (npmjs.com/settings/~/tokens — write and "bypass 2FA" first), then
  GitHub PATs, OAuth apps and SSH keys, then cloud keys
  (AWS — including Secrets Manager in every region you use — GCP, Azure), then
  everything else the process could read: .env files in any project you
  had open, kubeconfig, Vault tokens, database URLs, VPN, AI-service keys, wallet
  keys and seed phrases. Finally your clipboard — this family has a
  documented clipboard stealer, so a password pasted out of a manager while infected
  should be treated as seen.






  Step 2
  
Clean the machine

  
Before touching any repo

    
snare doctor          # machine, persistence spots, your GitHub account
snare guard scan      # one-shot process check
snare guard install   # kill the loader on sight, from login onwards

  
guard scan saying "clean" does not mean you
  were never infected. It reports what is running right now. The
  loader fires when a build runs or an editor opens the folder, does its work, and
  exits. A clean process check alongside infected repositories is the expected
  result, not a contradiction.






  Step 3
  
Clean the repositories

  
Dry run first — always

    
snare fix owner/repo                        # dry run, changes nothing
snare fix --all                             # dry run over everything flagged

snare fix owner/repo --push                 # clean the branch tips
snare fix owner/repo --purge-history --push # erase it from all history

  
--purge-history rewrites every commit, so every
  SHA changes. Collaborators must delete their clone and re-clone; a
  git pull will conflict or silently reintroduce old objects. Forks and
  pull-request refs keep the old objects regardless — ask GitHub Support to
  garbage-collect them if that matters to you.

  
Afterwards, verify rather than assume. snare scan github
  only reads branch tips; run snare scan repo against a fresh clone to
  walk full history.






  Step 4
  
Tell the others

  
Contacts and templates

    
snare notify owner/repo             # list collaborators, preview the notice
snare notify owner/repo --issue     # file a GitHub issue @-mentioning them
snare notify owner/repo --mail      # open a pre-filled mail draft per person

  
Both templates lead with credential rotation and say plainly that
  this is not an accusation: the malware injects from an already-infected machine, so
  a collaborator whose commit carried it was almost certainly a victim rather than a
  cause. Say that early, or you will not get the reply you need.






  If the count is high
  
If a lot of repositories are flagged

  
Fifteen infected repositories is not fifteen accidents. It points at one machine
  that pushed to all of them. Work out which machine that is before cleaning anything,
  or you will clean the same repositories twice.

  
Worth knowing what you scaffold new projects with — a starter
  template, a create-* command, a downloaded theme, an editor extension.
  The delivery mechanism for this family is still unidentified, and
  that is the single most useful thing anyone can contribute. If you find yours,
  say so in the
  discussion.

  After installing
  
The four commands that matter on day one

  
Four verbs. It uses your own GitHub credentials and ships no token of its own.

  

    

      snare guard install
      
Watch this machine

      
Detects the loader and kills it — process and children — within about a second, then saves
      the evidence. It only ever kills interpreters, so a shell that merely mentions an indicator is
      left alone.

    

    

      snare scan github
      
Scan every repo

      
Checks every repository you can reach through the API without cloning any of them.
      snare scan repo . goes deeper on a clone: working tree, every branch, full history.

    

    

      snare fix owner/repo
      
Clean it out

      
Writes a backup bundle first, always. Cleans branch tips, or purges the payload from every
      commit in history. Dry run unless you explicitly say otherwise.

    

    

      snare notify owner/repo
      
Warn your team

      
Files a GitHub issue mentioning your collaborators and opens a pre-filled mail draft for
      each one. It never sends anything — you send from your own account.

    npm run dev

  package.json:1 — "dev" runs api.js, a 29 KB obfuscated file

    Staying up to date
    
snare tells you when a new version is out, or installs it itself

    
A scanner is only as good as its last fix, so snare checks in the background,
    at most every six hours, and never slows a command down to do it. Choose what happens when it
    finds something:

    

      

        
ModeWhat happens

        
          
notify defaultOne line the next time you use snare:
          snare 1.9.1 is out (you have 1.9.0) — update: snare update.

          
autosnare installs it, restarts the guard, clears the old version's leftovers,
          then tells you once what changed. It only moves forward along main, never over local
          edits, and logs to ~/.snare/logs/auto-update.log.

    Auth
    
It uses your credentials, and stores none

    
snare ships no token of its own. Every GitHub call goes through the GitHub CLI
    using your account, which means it can only ever reach what you can already reach.

    
authenticate

      
gh auth login              # browser, or paste your own token
export GH_TOKEN=...        # or an env var

    
Scopes needed: repo and workflow. Do not use a
    token with broader permissions. A scanner does not need to administer your account,
    and a token that can do more is a token worth more to whoever steals it.

    

      
If you are here because you were compromised

      
Do not authenticate with a token that existed while the machine was infected. Rotate
      first, then log in with the new credential — the rotation
      order is here. This family harvests token files and environment variables, so a token
      you reuse is a token the operator may already hold.

    

  


  

    Extending
    
Adding your own detection patterns

    
All detection reads a single file. Add a pattern there and every command —
    scan, guard, hook, shield, CI — picks it up, with no code change.

    
iocs.txt — one extended regex per line, # for comments

      
# a wallet address seen in a new variant
0x[0-9a-fA-F]{40}

# a C2 hostname
eth\.blockscout\.com

    
Patterns are extended regular expressions, one per line, # starts a
    comment. The structural heuristic — code, a run of 50+ whitespace characters, then more code —
    runs independently of this list, which is why a variant using an address nobody has seen before
    is still caught.

    
If you write a pattern that catches something new,
    send it in. A variant nobody else can detect yet is the single most
    useful thing to contribute.

Chapter 06Every command8 min read

  
Every command, and what it will not do

  
snare is about 2,200 lines of bash. No framework, no
    npm install — deliberately, because npm is the attack surface. The core heuristic
    is language-agnostic; the config list is tuned for the JavaScript ecosystem, because that is
    where this family lives.







  
  

  
  
  

    Start here
    
The guided one

    
If you do not want to choose between the commands below, this runs the whole sequence and
    asks you at each step. It is the same work, in the order that actually helps.

    
Guided clean-up

      
snare respond                   walk through everything, one question at a time
snare respond --status          where you got to
snare respond --reset           start the walkthrough again

    
Six steps: check the machine, rotate credentials, clean the machine, find what
    is infected, fix it, tell your collaborators — then a verification pass that re-reads rather
    than trusting what just happened. Anything that writes to a repository defaults to
    no, and the choice to purge history is asked once rather than per repository.
    Progress is saved, so stopping and resuming is fine.

    
It refuses to run unattended. With no terminal, or CI set, it
    exits rather than prompting where nobody can answer — use the individual commands there.

  


  

    Find it
    
Scanning

    
Scanning

      
snare scan                      scan the current directory
snare scan repo [path]          one clone: working tree, all branches, full history
snare scan repo [path] --new    only findings that are not in the baseline
snare scan orgs                 list every org/account you can reach, with repo counts
snare scan orgs --all           include individual accounts, not just organisations
snare scan github               every repo you can reach, via the API (no cloning)
snare scan github --pick        choose which orgs to scan, from a list
snare scan github --owner a,b   only these orgs/accounts (comma-separated)
snare scan github --mine        only repos you own
snare scan github --all-branches
snare doctor                    this machine, persistence spots, and your GitHub account
snare selftest                  prove detection still works against known samples


    
Scanning everything is often the wrong first move.
    A real account reaches further than people expect — one we tested sees 22
    organisations and roughly 950 repositories, which is several thousand API calls.
    scan orgs lists what is reachable and how big each owner is, so you can
    start with the ones that matter; scan github --pick shows the same list
    and lets you choose from it. The repo counts are the number
    --owner will actually scan, not an estimate.


    
Read this before trusting a clean result.
    scan github reads branch tips through the API. It cannot see
    history, and it fetches a bounded set of files. A payload that was committed and
    later removed, or one hidden somewhere it does not look, will not appear.
    scan repo against a real clone is the thorough check — it walks every
    branch and every commit. The infection that started all of this survived a clean
    127-repository API sweep and was only caught by scan repo.


    
selftest exists because four defects once made snare
    report clean on infected repositories. It builds a scratch repo of known-bad
    and known-good samples, runs the real scanner, and exits non-zero on any mismatch.
    If it fails, do not trust any clean result until it passes.

  


  

    Stop it coming in
    
The gate, for you and for coding agents

    
Gate · agents

      
snare agents install            gate every clone, pull, install and run an agent does
snare agents status | uninstall
snare agents install --project  also this repo's CLAUDE.md / AGENTS.md and a project hook
snare gate -- <command>         scan first; exit 0 means safe to run it
snare gate allow [dir [branch]|url]  you looked and it is yours: allow what was flagged,
                                on disk or still incoming (a branch, a pull, a clone)
snare gate allowed | forget     review or withdraw what you allowed
snare gate report               the last block, word for word, to paste into an agent


    
A block is what snare suspects, not a verdict. It lists each
    finding as the file, the line and what is suspected, so you can look — it can be a false
    alarm. Then you decide: snare gate allow if it is yours, or
    snare respond to let snare take charge. Approvals live in
    ~/.snare, never in the repository, and lapse if the file changes. A coding agent
    cannot approve its own block: it is told to stop and show you, and an agent that tries is
    refused.


    
The gate answers one question before a command runs: does it
    bring code in or execute it, and is that code clean? git clone is cloned to a
    quarantine directory and scanned first. git pull, merge,
    rebase and checkout fetch — which runs nothing — and scan the incoming
    tree in a throwaway worktree before a file lands. Installs and npm run scan the
    directory they would run in. It fails closed: if the scan cannot finish, the command does not
    run.


    
For coding agents, snare agents install adds a
    Claude Code PreToolUse hook — enforced, so the agent cannot skip it — and a short
    instruction block in CLAUDE.md, AGENTS.md and GEMINI.md
    for agents without hooks. A block reads "FIRE ON THE MOUNTAIN", tells the agent to stop
    and tell you, and raises a desktop notification. Ordinary commands like git status
    cost about 30ms. install.sh and snare update show what it would change
    and ask first; after a yes, snare update keeps it current, and
    snare agents uninstall removes it and keeps it removed.

  


  

    Every ecosystem
    
Known-malicious packages: npm, Python, Rust, Go and more

    
Deps

      
snare deps [dir]                 lockfiles, node_modules and virtualenvs against the list
snare deps --system              also your global Python, pipx, npm and cargo installs
snare deps fix [dir]             remove each one, or replace it with a version not listed
snare deps update | status       refresh / show the known-malware list


    
The list is OpenSSF's
    malicious-packages database — about 117,000 packages across npm, PyPI, crates.io, Go,
    RubyGems, Packagist, NuGet and Maven — condensed every six hours into one small file.
    Every snare downloads the same file and matches it on its own machine, so
    nothing about your packages is ever sent. Lockfiles read: npm, pnpm, yarn, bun,
    requirements*.txt, poetry, uv, pdm, pylock.toml, Pipfile,
    Cargo.lock, go.sum, Gemfile.lock,
    composer.lock and NuGet's packages.lock.json.


    
The gate uses the same list: npm i x@1.2.3,
    npx, pip install x==1.0, uv add, cargo add,
    go get, gem install and composer require are stopped
    when the version is listed, and a repository's lockfiles are checked before
    npm install or pip install -r. It also treats the files other
    languages run on their own as routes: setup.py, conftest.py,
    build.rs, sitecustomize.py, .pth files (Python runs them at
    every start — the LiteLLM 1.107.0 payload was one) and //go:generate lines.

  


  

    Stop it running
    
Guard and shield

    
Guard · shield

      
snare guard install             kill the loader on sight, from login onwards
snare guard scan                one-shot check of this machine
snare guard status | log | stop | start | restart | uninstall

snare shield install            scan before npm/pnpm/yarn/bun/npx and git clone run
snare shield status | uninstall
snare shield check [path]       the fast check on its own (~22ms)


    
The guard is a background process (launchd on macOS,
    a systemd user unit on Linux, a logon Scheduled Task on Windows). It polls once per
    second, so a payload can still act before it is caught, and it cannot see code already
    running inside another process.


    
The shield wraps package managers in your shell so a
    scan happens before they can execute anything. Honest limits: it is shell-only, so it
    cannot see VS Code's own folderOpen task — that is the guard's job — and
    anyone can bypass it with command npm or SNARE_SKIP_SHIELD=1.
    It is a seatbelt, not a sandbox.

  


  

    Stop it spreading
    
Hook and CI

    
Hook · CI

      
snare hook install              block a push that carries a payload
snare hook install --with-pre-commit
snare hook status | uninstall

snare ci install                write a GitHub Actions workflow into this repo
snare ci status                 is the workflow installed, and is the check required?
snare ci print                  print the workflow without writing it


    
This family injects into commits from an already-infected machine,
    so the payload leaves before anyone scans a repository. The hook is the
    only feature that prevents that rather than detecting it afterwards. It also refuses the
    push when the machine itself has a live detection, because a clean repo pushed from an
    infected machine can still carry the payload out.


    
GitHub.com cannot reject a push outright — server-side
    pre-receive hooks are an Enterprise feature. A required status check is the practical
    equivalent: the merge button stays disabled until the scan passes. ci install
    writes the workflow, but you must tick it as required under
    Settings → Branches. Until you do, it reports and blocks nothing —
    snare ci status will tell you when that is the case.

  


  

    Clean up
    
Fix, rotate and notify

    
Fix · rotate · notify

      
snare fix <owner/repo>                        dry run (always backs up first)
snare fix <owner/repo> --push                 clean branch tips and push
snare fix <owner/repo> --purge-history --push erase it from all history
snare fix --all                               every repo the last scan flagged
snare fix --pick                              choose orgs, scan them, then fix
snare fix --pick --purge-history --push       ... and erase it from all history
snare fix --owner a,b --push                  the same, without the prompt

snare rotate                    what to revoke, in order, plus a GitHub audit
snare notify <owner/repo>       list collaborators and preview the notice
snare notify <owner/repo> --issue | --mail


    
Rotate before you clean. Stealing credentials is what
    this family is for; the file in your repository is delivery, not payload.
    Removing it does not un-steal a token. snare rotate lists what to revoke
    in order — npm write tokens first, because a stolen one lets the worm publish
    trojanised versions of your other packages under your name — and audits your GitHub
    account for the repositories and secret-exporting workflows this family leaves behind.
    The full sequence is on the response page.


    
fix --pick is the whole clean-up in one pass:
    choose organisations from the same list scan orgs prints, scan them, then
    remediate what was found. It is a dry run unless you add --push, and the
    destructive flags stay on the command line rather than hiding inside a friendlier verb —
    force-pushing rewritten history across an organisation should be legible in your shell
    history. --owner a,b is the same thing without the prompt, for a script or a
    timer. With --purge-history it checks for git-filter-repo
    before scanning, rather than after asking you to choose and then failing on the
    first repository.


    
--purge-history rewrites every commit, so every SHA changes.
    Collaborators must re-clone, not pull, and forks and pull-request refs still
    hold the old objects. fix --all is a dry run by default and requires you to
    type the repository count to confirm, because it can force-push.

Reports, baseline and update

    
Reports · baseline · update

      
snare report                    scan, save a timestamped report
snare report --json             machine-readable; exits non-zero on findings
snare schedule install --daily  run it on a timer and notify on findings

Reports write to $SNARE_HOME/reports and exit non-zero when
    something is found, so a timer or a CI job can act on the result. There is deliberately
    no email: SMTP credentials in a security tool are a liability, and a
    report file plus a native notification does the same job with nothing worth stealing.

    make it safe. Only baseline what you have actually read.

    before 27 August 2026 contains defects that made the working-tree scan report
    clean on infected repositories. If you installed snare before then, update
    before you trust it, and run snare selftest afterwards. The
    changelog lists every one of them.

  


  

    Limits
    
What snare does not do

    
A security tool that oversells itself is worse than no tool at all.

    

      
The guard polls once per second, so a payload can still act before it is caught. It cannot
      see code already running inside another process, and it will miss variants built on different
      infrastructure. Removing the malware from the repository is the actual fix — a
      running guard is never permission to open a repo you do not trust.

      
Scanning through the GitHub API sees branch tips only. A payload that was
      committed and later deleted survives in history; use snare scan repo on a clone to
      catch that.

      
Rewriting history does not touch forks, pull-request refs, or objects still
      reachable by SHA. Ask GitHub Support to garbage-collect after a purge.

1.9.0

      7 Nov 2026
        Current
      Release notes ↗
    

    
snare update now restarts the guard and cleans up after itself. And snare tells you when there's a new version, or installs it for you.

    

      
Changed — snare update finishes the job

      
    
        
  • The background guard is restarted for you. After every update people were told to run snare guard stop && snare guard start, and a guard nobody restarted kept running the previous version. snare update now restarts it on the new code, rewriting its service file first. It also catches a guard that is still on an older version even when there is nothing new to pull. The guard records its version when it starts, and snare guard restart does the same by hand.
    • 
        
  • Leftovers are cleared. The gate's cached verdicts from the old version are removed, since they are keyed by version and can never be used again. So are blocks waiting for snare respond in repositories that no longer exist, logs past 1 MB (trimmed to their most recent part) and stale refresh markers. Backups, reports and evidence are never touched.
    • 
      

    

    

      
Added — snare tells you when a new version is out, or installs it

      
    
        
  • snare update --mode notify|auto|off. - notify (the default): snare checks in the background at most every six hours and tells you "snare X is out (you have Y) — update: snare update". - auto: snare installs new versions itself, then says once what changed. It only fast-forwards from main, never touches an install with local edits, and logs to ~/.snare/logs/auto-update.log. - off: never check.
    • 
        
  • The background check now also runs when snare is used by a coding agent. Before, it ran only at a terminal, so installs used mostly through agents never learned about a new version.
    •

1.7.0

      6 Nov 2026
      Release notes ↗
    

    
snare update now actually updates.

    

      
Fixed — snare update said "already up to date" and never updated

      
    
        
  • snare update updated whichever branch the install happened to be on. An install left on any other branch (an old work branch, a branch someone checked out to test a fix) fetched that branch, found nothing new, and answered "already up to date" on every run. Meanwhile snare version compared against main and said "behind". Both were right about different branches, and the install never moved.
    • 
        
  • Updates now always come from main, where releases are published. An install on another branch is moved to main when everything on that branch is already in main. A branch carrying commits main does not have is someone's work: it is left alone, and snare prints the exact command to switch. snare update --check and the "behind" notice now measure against main as well, so they agree with what snare update does.
    • 
        
  • If you are stuck on an older version that has this bug, run once: cd ~/snare && git checkout main && snare update.
    • 
      

    

    

      
Fixed — on Linux, every agent command re-downloaded the malware list
